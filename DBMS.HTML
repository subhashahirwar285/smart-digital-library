Preface

Database Management System is an essential subject in computer science. Almost every modern application uses a database to store and manage information, from college records and library catalogues to banking and online shopping.

This textbook introduces database concepts step by step. It covers database architecture, data models, keys, ER diagrams, normalization, SQL, joins, transactions, concurrency, indexes, security and modern NoSQL systems.

How to use this book: Read the explanation in each chapter, write the sample SQL statements in a database such as SQLite or MySQL, and test them with your own sample records.

Learning Outcomes

  • Understand database and DBMS fundamentals.
  • Identify entities, attributes, relationships and keys.
  • Design tables and understand normalization.
  • Write SQL queries to create, retrieve and modify data.
  • Understand transactions, concurrency, security and recovery.
  • Plan a database for a practical application such as a library.

Chapter 1: Introduction to DBMS

1.1 Meaning of Database

A database is an organised collection of related data. It stores information in a structured way so that users and applications can retrieve, add, change and remove records.

1.2 What is DBMS?

A Database Management System (DBMS) is software that allows users to define, create, maintain and control access to databases. Examples include MySQL, PostgreSQL, Oracle Database, Microsoft SQL Server and SQLite.

1.3 Need for DBMS

A DBMS reduces unnecessary duplication, improves consistency, supports multiple users, provides security and helps recover information after failures.

1.4 Applications

DBMS technology is used in banks, railway reservations, hospitals, colleges, e-commerce, libraries, payroll and inventory systems.

1.5 Database System Components

A database system includes the data, DBMS software, hardware, application programs, procedures and people such as database administrators, developers and end users.

Practical Example / Application:

A college library can store student details, book information, issue records and return dates in a database instead of maintaining separate paper registers.

Chapter 2: File System and DBMS

2.1 File Processing System

In a file processing system, each application maintains its own files. Different departments may store repeated copies of the same information.

2.2 Limitations of File System

Common problems include data redundancy, inconsistency, difficult data access, isolated data, weak security, concurrent access problems and difficult backup.

2.3 DBMS Approach

A DBMS provides a centralised and controlled way to store related data. Applications access information through queries and database services.

2.4 DBMS vs File System

A DBMS generally offers structured querying, constraints, access control, transactions, concurrency control and recovery. File systems may be simpler for small standalone tasks.

2.5 When to Use DBMS

A DBMS is useful when information is shared, relationships matter, records change frequently or reliable access and security are required.

Practical Example / Application:

If a student's phone number is saved in three independent files, changing only two copies creates inconsistent information. A central student table avoids this kind of repeated update.

Chapter 3: Database Architecture

3.1 Three-Schema Architecture

The three-schema architecture separates the user view, the logical structure and the physical storage of a database.

3.2 External Level

The external level describes the part of the database visible to a particular user or application. Different users can have different views.

3.3 Conceptual Level

The conceptual level describes the overall logical structure, including entities, relationships and constraints.

3.4 Internal Level

The internal level describes how data is physically stored, such as files, indexes and storage structures.

3.5 Data Independence

Data independence means changes at one schema level can be made with limited effects on other levels. Logical data independence concerns conceptual changes; physical data independence concerns storage changes.

Practical Example / Application:

A student may see book search and issue details, while a librarian may also see member records and issue-management screens. Both can use the same database through different views.

Chapter 4: Data Models

4.1 Meaning of Data Model

A data model defines how data, relationships and constraints are represented in a database.

4.2 Hierarchical Model

The hierarchical model organises records in a tree structure. A child record generally has one parent.

4.3 Network Model

The network model represents records connected through links and can support more complex relationships.

4.4 Relational Model

The relational model organises data into tables consisting of rows and columns. Relationships are represented using keys.

4.5 Object and Document Models

Object models represent data as objects. Document databases store flexible documents, often in JSON-like structures.

Practical Example / Application:

In a relational library database, STUDENT, BOOK and ISSUE can be separate tables connected through student and book identifiers.

Chapter 5: Relational Model and Keys

5.1 Basic Terms

A relation is a table, a tuple is a row, an attribute is a column and a domain is the set of permitted values for an attribute.

5.2 Primary Key

A primary key uniquely identifies each row in a table. It must contain unique, non-NULL values.

5.3 Candidate and Alternate Keys

A candidate key is a minimal set of attributes that uniquely identifies a row. A candidate key not selected as the primary key is an alternate key.

5.4 Foreign Key

A foreign key is an attribute or group of attributes that refers to a candidate key, commonly the primary key, in another table.

5.5 Composite and Unique Keys

A composite key uses more than one attribute. A unique constraint prevents duplicate values in the constrained column or column group.

Practical Example / Application:

A Student table can use StudentID as its primary key. An Issue table can store StudentID as a foreign key referring to Student.

Chapter 6: Entity Relationship Model

6.1 Entity and Entity Set

An entity is a distinguishable real-world object, such as a student or book. An entity set is a collection of similar entities.

6.2 Attributes

Attributes describe entities. They may be simple, composite, single-valued, multi-valued or derived.

6.3 Relationships

A relationship represents an association between entities. For example, a student borrows a book.

6.4 Cardinality

One-to-one, one-to-many and many-to-many describe how many entity instances can participate in a relationship.

6.5 ER Diagram Symbols

Rectangles commonly represent entities, ovals represent attributes, diamonds represent relationships, and lines connect them.

Practical Example / Application:

A library has STUDENT and BOOK entities. Their many-to-many borrowing relationship can be represented using an ISSUE entity containing issue date and return date.

Chapter 7: Normalization

7.1 Meaning and Purpose

Normalization organises relational tables to reduce avoidable duplication and prevent insertion, update and deletion anomalies.

7.2 Functional Dependency

A functional dependency X → Y means that a value of attribute set X determines a value of attribute set Y.

7.3 First Normal Form (1NF)

A table is in 1NF when each cell contains an atomic value and repeating groups are removed.

7.4 Second Normal Form (2NF)

A table is in 2NF when it is in 1NF and every non-key attribute depends on the whole candidate key, not only part of a composite key.

7.5 Third Normal Form (3NF)

A table is in 3NF when it is in 2NF and non-key attributes do not have inappropriate transitive dependencies on a candidate key.

7.6 Benefits

Normalization improves consistency and makes updates more reliable. Some systems use carefully chosen denormalization for performance.

Practical Example / Application:

Instead of storing several book titles in one cell, create one row per book. Keep student details in STUDENT and borrowing details in ISSUE.

Important Questions

Chapter 8: SQL Introduction and DDL

8.1 What is SQL?

SQL stands for Structured Query Language. It is used to define, query and manipulate data in relational database systems.

8.2 DDL

Data Definition Language commands define database structures. Common commands include CREATE, ALTER, DROP and TRUNCATE.

8.3 CREATE

CREATE TABLE defines a new table and its columns, data types and constraints.

8.4 ALTER and DROP

ALTER changes a database object structure. DROP removes a database object such as a table.

8.5 Constraints

Constraints such as PRIMARY KEY, FOREIGN KEY, NOT NULL, UNIQUE and CHECK help enforce valid data.

Practical Example / Application:

CREATE TABLE Student (StudentID INTEGER PRIMARY KEY, Name VARCHAR(60) NOT NULL, Email VARCHAR(100) UNIQUE);

Chapter 9: DML, DQL and SQL Queries

9.1 DML

Data Manipulation Language commands insert, update and delete table data. Common commands are INSERT, UPDATE and DELETE.

9.2 SELECT

SELECT retrieves data from one or more tables. WHERE filters rows according to a condition.

9.3 Sorting and Distinct Values

ORDER BY sorts query results. DISTINCT removes duplicate result rows.

9.4 Aggregate Functions

COUNT, SUM, AVG, MIN and MAX calculate summary values over rows.

9.5 GROUP BY and HAVING

GROUP BY forms groups for aggregate calculations. HAVING filters groups after aggregation.

Practical Example / Application:

INSERT INTO Student(StudentID,Name) VALUES (1,'Aman'); SELECT * FROM Student; UPDATE Student SET Name='Aman Kumar' WHERE StudentID=1;

Chapter 10: Joins, Subqueries and Views

10.1 Joins

A join combines rows from two or more tables using a related column or join condition.

10.2 INNER JOIN

INNER JOIN returns rows that satisfy the join condition in both tables.

10.3 LEFT and RIGHT JOIN

LEFT JOIN preserves all rows from the left table and matching rows from the right. RIGHT JOIN does the corresponding operation from the right side.

10.4 Subquery

A subquery is a query nested inside another SQL statement. It can be used in conditions, derived tables or expressions.

10.5 Views

A view is a named query that behaves like a virtual table. Views can simplify complex queries and limit which columns users see.

Practical Example / Application:

SELECT Student.Name, Issue.IssueDate FROM Student INNER JOIN Issue ON Student.StudentID = Issue.StudentID;

Chapter 11: Transactions and ACID Properties

11.1 Transaction

A transaction is a logical unit of database work containing one or more operations.

11.2 Atomicity

Atomicity means all operations in a transaction succeed together or the transaction is rolled back.

11.3 Consistency

Consistency means a committed transaction preserves defined database rules and constraints.

11.4 Isolation

Isolation controls how concurrent transactions interact and helps prevent interference between them.

11.5 Durability

Durability means committed changes remain saved even after a system failure, subject to the database's guarantees.

11.6 COMMIT and ROLLBACK

COMMIT makes a transaction's changes permanent. ROLLBACK cancels changes that have not been committed.

Practical Example / Application:

When a bank transfer debits one account and credits another, both operations should be treated as one transaction so that only one side is not committed alone.

Important Questions

Explain ACID properties. Differentiate COMMIT and ROLLBACK.

Chapter 12: Concurrency Control and Deadlocks

12.1 Concurrent Transactions

Concurrency occurs when multiple transactions execute during overlapping periods. It improves resource use but requires control.

12.2 Lost Update

A lost update can occur when one transaction overwrites another transaction's change without properly accounting for it.

12.3 Locks

Shared locks generally support reading, while exclusive locks are used for writing. Locking helps coordinate access to shared data.

12.4 Serializability

A schedule is serializable when its effect is equivalent to some serial execution of the transactions.

12.5 Deadlock

A deadlock occurs when transactions wait indefinitely for resources held by one another. Systems may detect, prevent or recover from deadlocks.

Practical Example / Application:

If two transactions update the same account record at nearly the same time, concurrency control helps ensure that the final balance is correct.

Chapter 13: Indexes and Query Processing

13.1 Index

An index is a data structure that helps a DBMS find rows more efficiently, often by avoiding a full table scan.

13.2 Advantages and Costs

Indexes can speed up reads but require storage and can add work to INSERT, UPDATE and DELETE operations.

13.3 Clustered and Non-Clustered Concepts

Some database systems organise table data around a clustered index; non-clustered indexes maintain a separate lookup structure. Exact behaviour varies by DBMS.

13.4 Query Processing

A DBMS parses SQL, checks it, chooses an execution plan and runs operations to produce results.

13.5 Query Optimization

The query optimizer compares possible execution strategies using information such as indexes, table sizes and statistics.

Practical Example / Application:

CREATE INDEX idx_student_email ON Student(Email); can help searches that filter by Email, depending on the DBMS and query plan.

Chapter 14: Database Security, Backup and Recovery

14.1 Database Security

Database security protects information from unauthorised access, alteration, disclosure or destruction.

14.2 Authentication and Authorization

Authentication verifies who a user is. Authorization determines what that user is allowed to do.

14.3 Roles and Privileges

Privileges such as SELECT, INSERT, UPDATE and DELETE can be granted to users or roles according to their responsibilities.

14.4 Backup

A backup is a copy of database information used to restore data after accidental deletion, corruption or hardware failure.

14.5 Recovery

Recovery procedures restore a database to a consistent state. Depending on the system, logs, checkpoints and backups may be used.

14.6 Good Practices

Use least privilege, secure credentials, apply updates, protect backups and regularly test restoration procedures.

Practical Example / Application:

A library assistant may need permission to issue and return books, while only an administrator may manage user accounts and database settings.

Important Questions

Differentiate authentication and authorization. Explain backup and recovery.

Chapter 15: NoSQL and Distributed Databases

15.1 NoSQL Meaning

NoSQL databases support data models beyond the traditional relational table model and are often used for flexible or large-scale data workloads.

15.2 Key-Value Stores

A key-value database stores values associated with unique keys. It is useful for simple lookups and caching.

15.3 Document Databases

Document databases store records as documents, commonly in JSON-like formats, which can support flexible fields.

15.4 Column-Family and Graph Databases

Column-family systems organise data around column families. Graph databases represent entities as nodes and relationships as edges.

15.5 Distributed Databases

A distributed database stores or replicates data across multiple computers or locations. Design choices affect availability, consistency and performance.

Practical Example / Application:

A relational DBMS may store a fixed student and issue schema, while a document database may store a flexible profile document with optional fields.

Important Questions

What is NoSQL? Explain key-value, document, graph and column-family databases.

Chapter 16: Database Design Case Study: Library System

16.1 Requirements

Identify users and operations: register students, maintain books, search the catalogue, issue and return books, and produce reports.

16.2 Main Entities

Typical entities include STUDENT, BOOK, CATEGORY, ISSUE and USER. Each entity should have a suitable primary key.

16.3 Relationships

A category can contain many books. A student can have many issue records. Each issue record refers to one student and one book.

16.4 Example Table Design

STUDENT(StudentID, Name, Email); BOOK(BookID, Title, CategoryID); CATEGORY(CategoryID, CategoryName); ISSUE(IssueID, StudentID, BookID, IssueDate, ReturnDate).

16.5 Testing and Maintenance

Test valid and invalid records, duplicate keys, missing values, issue/return workflows, concurrent access and backup restoration.

Practical Example / Application:

A simple design can use STUDENT, BOOK, CATEGORY and ISSUE tables. ISSUE stores foreign keys to STUDENT and BOOK, along with dates and return status.

Important Questions

Design a database for a library. Identify entities, primary keys and relationships.

Glossary

  • Attribute: A named property or column of a relation.
  • Candidate Key: A minimal attribute set that uniquely identifies a row.
  • DBMS: Software used to create, manage and control databases.
  • DDL: SQL commands used to define database structures.
  • DML: SQL commands used to insert, update and delete data.
  • Entity: A distinguishable real-world object represented in a database.
  • Foreign Key: A column or column group referring to a key in another table.
  • Normalization: Organising tables to reduce redundancy and anomalies.
  • Primary Key: A key selected to uniquely identify each row.
  • Query: A request to retrieve or manipulate database information.
  • Relation: A table in the relational model.
  • SQL: Structured Query Language.
  • Transaction: A logical unit of database operations.
  • Tuple: A row in a relational table.
  • View: A named query presented like a virtual table.
